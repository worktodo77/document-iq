# D-32 executed — the publication protocol is gone, and here is exactly what that costs

**This file:** `docs/verification/d32_descope_2026-08-06.md`
**Branch:** `build/s2-descope` (off `build/sprint-2` @ `d996532`) · **Date:** 2026-08-06
**Ruling implemented:** D-32 (`docs/decisions/decision_register.md`, "D-32 EXECUTED")
**Author:** Claude (Opus 5)

Measured, not expected. §8 names what nothing here supports.

This note states the rule and the window **in its own words**, not by reference,
because that is what the ruling asked for and because a note that forwards the
reader to a docstring for the one thing they came to read has not said it.

---

## 1. The rule, in one sentence

> **Publication deletes the previous run's deliverables from the matter folder
> and then moves each staged file onto its final name, in that order, once —
> with no marker, no set-aside copy, no inventory, and no recovery.**

That is the whole of `dociq.emit.paths.publish_staging`. It is 40 lines of code
with three failure branches, and there is no state on disk for it to read or
write. The previous design was a four-phase state machine over three durable
files, a pure classifier with five outcomes, and a recovery entry point every run
called before it read anything.

## 2. The window it leaves open, at full width

Between the first removal and the last move, **the matter folder holds part of
the previous run's evidence and part of this run's.** A process that dies inside
that window — power loss, a kill, an unhandled crash in code publication does not
own — leaves it that way **permanently**:

* nothing on disk records that a publication was in progress;
* no later run detects the mixture, repairs it, or warns that it happened;
* `output_manifest.json` is itself one of the files that may or may not have
  landed, so the folder's own description of itself may belong to either run;
* a later run *will* end the mixture, but only because it replaces everything,
  and only if that run itself succeeds.

**How wide is it, in time?** It is one removal per superseded name plus one
rename per staged file. On the fixture corpus that is 30-odd files and the window
is milliseconds; **on the measured MODEC corpus (368 documents, 17,732 pages) it
is thousands of `clean_text/*.txt` files, so the window is seconds, not
milliseconds.** It is not a theoretical instant and this note will not describe
it as one.

**The one thing that survives a crash in the window:** the new set. Publication
removes the staging tree only after every file has been moved out of it, so an
interrupted publication leaves the complete new deliverables under
`.dociq/staging/`. The next run reports having found that tree
(`run.state_residue_before_run` in the processing log) before discarding it. That
report is the **only** trace that anything went wrong, and it says "a run did not
finish", not "this folder is mixed" — because nothing can tell the difference
between a run that died during emit and one that died during publication.

**What the operator is told when the failure is a handled one** (an I/O error
rather than a process death): `PublicationFailed`, whose message begins "THIS
FOLDER IS NOW MIXED", says how many of how many steps completed, says DocIQ will
not repair it, and names the staging directory that still holds the new set. It
is not caught by `pipeline.run` — converting it into a refused run would file a
mixed matter folder under a status that means "nothing was touched".

**This is the trade Alex ruled**, and it is a worse hole than any of the nine
findings the sixth review generation produced: one hole that fits in a sentence,
in place of many that hide. It is recorded here in the same words as the register
so that nobody has to reconstruct it: *a simpler design with a larger known risk,
chosen over a complex one with a smaller unknown one.*

## 4. What was kept, and why each earns its place

* **B-1's publication gate — unchanged.** A red Stage 6 (accounting not OK,
  unclassified manifest output, corpus-order disagreement, un-hashable log
  content) still refuses, still routes through `_abort`, still produces
  `TerminalStatus.REFUSED`, `incomplete_run/`, and B-5's durable diagnosis.
  **This is why the staging directory survived the descope**: the audit runs over
  the staged set, so a failed gate costs a run and never an evidence set.
  `tests/test_publication_gate.py::test_the_swap_is_unreachable_without_passing_the_gate`
  is a source-level probe that publication is downstream of the gate; it was
  watched red with publication moved above it.
* **The staging directory itself.** Removing it would reintroduce B-1 exactly.
  What D-32 removed is the publication *protocol*, not the place deliverables are
  built. Crash-during-emit still leaves the previous run byte-for-byte intact,
  proven over four crash points.
* **The package's assemble-in-`incoming` order and A-6's recover-before-cleanup**
  in `emit/handoff.py` — untouched. That is a separate mechanism, the sixth
  review checked it, and `tests/test_package_swap.py` passes unmodified.
* **A-16 / A-17 residue disclosure** — see §5.
* **Determinism (criterion 7).** Nothing about publication reaches hashed
  `content`. Proven two ways: two destinations produce one identity and identical
  bytes; and a run into a folder with a previous set produces the same hashed
  content as a run into an empty one, so *what publication had to do* is not part
  of the run's identity.
* **`_remove_or_fail`'s B-4 reasoning.** A destructive step that cannot prove the
  name is gone must not report success. `ignore_errors` survives in exactly two
  places, both argued in place: discarding an unfinished staging tree, and
  removing the drained one.

## 5. Residue, in the narrower form it now takes

`emit.paths.state_residue()` replaces `superseded_residue()`. It reports
`.dociq/` trees DocIQ left behind:

* **`.dociq/staging`** — a run that did not finish. Measured at the *top* of a
  run (before `staging_layout` creates this run's own), which is load-bearing
  rather than incidental, and disclosed as `run.state_residue_before_run`.
* **`.dociq/superseded*`** — a set-aside tree from the removed protocol. Nothing
  in this build creates one; it is recognized so that a matter folder touched by
  the pre-descope branch build does not keep a full copy of an old evidence set
  unmentioned under `.dociq/`.

On the **success** path, `PublishResult.residue` is non-empty only when the
drained staging tree could not be removed — **empty directories**, since every
file left first. That is a smaller thing than A-16 was raised for, and §6 records
it as a stop-the-line disclosure rather than editing the amendment's meaning
quietly.

## 8. What nothing here supports

* **No real interrupted-publication event has been observed on a real matter.**
  Every window in this subsystem, across all six generations, required a Windows
  lock or a process death at a precise instant, and none has ever been seen in a
  real run. The window is argued from the code's shape, not from an incident.
* **The "seconds, not milliseconds" figure is arithmetic, not a stopwatch.** It
  is one filesystem operation per file over a corpus measured at 368 documents;
  it has not been timed on the real corpus, because doing so would require a
  full-corpus run this branch did not do.
* **`state_residue`'s legacy `superseded*` branch is untested against a folder a
  real pre-descope build left**, because no such folder exists outside a branch
  worktree. It is tested against a hand-built tree of the same shape.
* **The mixed-folder tests simulate a process death by raising inside
  `os.replace`.** That reproduces the *state*, not the mechanism; a genuine power
  cut could also leave a partially-written filesystem journal, which is outside
  anything DocIQ can test or promise.
* **No claim is made that the new design is correct** — only that it is small
  enough to enumerate. The three failure branches in `publish_staging` are all
  tested; the claim that they are *all* the branches rests on reading 40 lines.

### 9.2 Repetition — 38 runs, all green

Run sequentially on a verified-quiet machine (see 9.3):

|---|---|---|---|

The lock-dependent tests use **real open handles**, not injected exceptions:
`test_a_locked_previous_deliverable_stops_publication_before_any_move` holds a
matter-folder deliverable open, and
`test_a_failed_move_leaves_the_unmoved_staged_files_on_disk` holds a staged

`_retry_io`'s real 2.54 s budget on every one of the 30 repeats.

### 9.3 A measurement failure, recorded because it nearly became a false green

**The first campaign's numbers were contaminated and are withdrawn.** Repeated
restarts of the runner left **six** campaign shells alive — stopping the
background task killed the wrapper, not the process tree — so up to twelve pytest
processes ran concurrently while results were being recorded. Two consequences,
both instructive:

* one full-suite run reported failures in `tests/test_offline.py`
  (`test_every_child_process_entry_point_is_restored_on_exit`,
  `test_the_platform_version_probe_runs_and_is_recorded`), both asserting that a
  child process produced output and both getting empty;
* a "PASS" line was recorded beside that failure text, because concurrent runs
  were overwriting each other's log files in `/tmp` — **the verdict and the
  evidence came from different processes.**

All strays were killed, absence verified by process listing, and the whole
campaign re-run sequentially. The `test_offline` pair is outside this change —
neither `emit/paths.py` nor `pipeline.py` spawns a child process — and it passed
in **all 8** clean full-suite runs. It is **not** attributed to the contention:
§9.4 records that the obvious explanation was tested and did not hold.

The lesson worth keeping: a runner that writes its verdict and its evidence to
paths another instance of itself can overwrite will eventually report a pass over
a failure, and no amount of repetition detects it.

### 9.4 The `test_offline` pair — UNREPRODUCED, and not attributed

The two failures in §9.3 were observed **once**, in a contaminated run. Both
hypotheses were then tested, and **neither was confirmed**:

| probe | runs | result |
|---|---|---|
| `tests/test_offline.py` alone, quiet machine | 5 | 5 PASS |
| full suite, quiet machine (the §9.2 campaign) | 8 | 8 PASS — `test_offline` green in every one |
| full suite, **six concurrent instances**, deliberately reproducing the conditions the failure was seen under | 6 | 6 PASS |

So the convenient explanation — "it was just contention" — is **not supported**.
The load probe was built specifically to confirm it and did not. The failure
remains **unreproduced and its cause unestablished**, and it is recorded that way
rather than closed with the explanation that would have been easiest to write.

What can be said with evidence:

* it is **outside this change**. Neither `emit/paths.py` nor `pipeline.py`
  spawns a child process, and both failing assertions are about a child process
  producing output;
* it has never been seen on a quiet machine, in 13 full-suite runs and 5 targeted
  runs;
* it was seen in a process where at least six other pytest trees were running,
  but that condition was reproduced six ways and did not trigger it.

**Treated as a real defect until shown otherwise**, per this project's standing
rule that a flaky probe is a defect: it is reported to Alex as an open item on
`tests/test_offline.py`, unfixed and out of D-32's scope, rather than absorbed
into this note as noise. A one-in-N flake in the guard that proves DocIQ makes no
network or child-process calls is worth someone's afternoon, because the test
exists to support an offline claim the product makes to a client.

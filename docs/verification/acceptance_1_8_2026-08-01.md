### Three decisions worth naming

**The scope statement's POSITION is part of the requirement.** D-20 rules that
every Path A package is a subset unless it says otherwise. A caveat printed
under a "368 documents, 18,556 pages" headline is read *after* the belief it
exists to prevent has formed, so the statement is the first thing in
`README_START_HERE.txt` — before the title, before any count. It is also
repeated inside the pasteable PROJECT INSTRUCTIONS block, because the README is
one file among hundreds in a Project's knowledge and the instructions field is
what actually steers the model. A scope that lives only in a file nobody quotes
is not a scope the analysis ever sees.

**A subset package's `sources.json` and `document_index.csv` are filtered.**
Copying them whole handed the reader a manifest naming documents the folder does
not contain — and §7 makes `sources.json` the thing Expert Assist reads to
*find* text, so every one of those names is a path that resolves to nothing. The
matter folder's own copies are never touched; filtering happens on the way into
the package.

**The package's token figure is re-measured over the selected documents.**
Reading `RunOutcome.tokens_after` would put the whole corpus's figure in a
twelve-document package's README — and the README's capacity sentence is
*derived* from that figure, so the error would arrive as advice.

### One duplication, structural rather than careless

The pagemodel freeze forbids the GUI importing `dociq.emit`
(`tests/test_import_graph.py`), so §8's whole-record scope wording has two
authors: `emit.handoff.default_scope_statement` and
`gui.view_models.PackageScope.statement`. A single shared author is not
available to both. `test_scope_statement_authors_agree_on_the_whole_record_wording`
binds them character-for-character over four cases — if either drifts, the
operator reads one sentence on screen and the recipient reads another.

## 2. Criterion 8 — §8's "only the sanctioned files" rule, asserted

§8's load-bearing sentence is that the package contains *only* the files
intended for upload. Its failure mode is specific and bad: `processing_log.json`,
`run_summary.pdf`, `output_manifest.json`, `doc_ids_issued.json`,
`reconciliation.csv` and the matter's profile copy are **DocIQ's own audit
trail**, and uploading them puts the tool's internals into the evidence corpus,
where an analyst can quote them back as if they were project records.

That rule was implemented and never checked. It is now `assert_only_sanctioned`,
which **raises** rather than warns — a package is dragged into a Project whole,
so there is no step at which an operator reads a warning about an extra file
before the upload happens. It walks the tree rather than listing the top level,
because a subdirectory of audit files passes a top-level check and uploads just
the same. It runs on every `build_upload_package` call, against what is **on
disk** rather than against what the function believes it wrote — the two differ
exactly when something else put a file there.

The class is enumerated in
`test_every_non_sanctioned_output_is_caught`: all six §7 deliverables that are
not one of §8's three, plus a nested text file and DocIQ's own `.dociq/` run
state.

### The wall clock is an UPPER bound, and the reason is not decoration

The machine was **not idle**. Throughout the run another agent's OCR job
(`tools/bates_acceptance.py`) and repeated `pytest` processes ran concurrently;
sampled CPU load was **100% for most of the observation window**, and at one
sample the competing job had accumulated 13,728 CPU-seconds. 103.0 minutes is
therefore what this corpus cost **on a contended 32-core box**, and a clean
idle-machine figure is still not established. It is quoted as an upper bound and
must not be restated as a throughput rate. §10's 60-minute target is missed,
which the register already declines to restate.

### The shipped per-file timeout bit — on SIX documents, not two

Six PDFs were abandoned inside the extraction pool at the shipped 3,600 s
per-file limit and then **re-read serially and recovered in full** (228, 222,
186, 189, 191 and 187 pages; "no degradation"). Nothing was lost and nothing was
silent — the watchdog and the load-dependent-extraction check both wrote it into
the run's warnings, and the serial read is what the run recorded.

The register's §10 restatement recorded **two** such documents on an idle
machine. This run saw **six** on a contended one, which is direct evidence that
the threshold is **load-dependent** rather than a property of six particular
files. That also locates most of the wall clock: the serial-recovery phase alone
ran from 5,259 s to 6,164 s.

**This is NOT fixed here, and that is a decision rather than an oversight.**
See §9.3.

### One document failed, and it is the document's fault

`…/CER-1-345.docx` failed in the pool *and* on the serial re-read — "UNCHANGED:
the serial read reproduced the same outcome, so this is a property of the
document, not of the load." Its content sniffs as a zip-family container that is
not a readable Word file. It is recorded `Failed` in the index, and it is the
one empty file in `clean_text/`.

### A 35-page difference from the previous full run, unexplained

This run: **18,556** pages. The register's completed run: **18,521**. The
difference is exactly 35, and Sprint-1's open finding is "a 9 MB PowerPoint
extracted as 35 pages on one full-corpus run and failed on another". All 17
`.pptx` documents processed `Full` here. That is **consistent with** the open
finding and is **not proof of it** — the earlier run's per-document page counts
are not in hand, so the coincidence of the number is the whole of the evidence.
The finding stays open; nothing here closes it.

## 9. What is NOT proven

### 9.1 "Accepted by a Claude Project" was NOT observed, and cannot be offline

Criterion 8's Path A wording is *"produces a package accepted by a Claude
Project without file-type or size rejections."* **Acceptance was not observed and
this note does not claim it.** Uploading is a network action; Principle 4 admits
no network access of any kind, and §12 excludes programmatic upload outright. No
package was uploaded, by DocIQ or by anyone.

What *is* established, by inspection of a package built from the real run:

* every file is `.txt`, `.json` or `.csv` — no format a Project could reject on
  type, and no binary, archive or executable;
* the largest file in the scoped package is **77 KB** and in the whole-record
  package **1.05 MB**, against a 30 MB per-file assumption — nothing is within
  an order of magnitude of it;
* the file **count** is 18 (scoped) and 371 (whole record);
* the folder contains only the files §8 sanctions, asserted;
* the README is present, readable, and leads with the scope.

What remains unverified, precisely:

1. **That a Claude Project accepts the upload.** Not observed. Only a person
   with a browser can establish it, and they should — this is the one part of
   criterion 8 that a human step closes.
2. **The limits themselves.** `ProjectLimits` is *operator-configurable
   assumptions, not fetched facts*: 30 MB per file is assumed and the file-count
   limit is **not enforced at all**. The package check reports that in words
   ("file-count limit not enforced: DocIQ is offline and cannot confirm the
   current Claude Project file-count limit") rather than passing a check it did
   not run. A 371-file upload could still be refused on count and nothing here
   would have predicted it.
3. **`DIRECT_CONTEXT_TOKENS = 200,000`.** D-21 rules the value; nothing has
   measured it. "84% of direct-context capacity" is 84% of a *ruled reference
   line*, not of a confirmed limit.
4. **The token figures are estimates under stated assumptions.** No real
   tokenizer was run — none can be, offline. "Fits directly" means "fits under
   DocIQ's estimate against DocIQ's reference line."

### 9.2 What Path B's proof does and does not cover

`expert_assist_layout` and the format probe establish that the folder has the
right names, in the right places, with §7-conformant contents, and that
`sources.json` resolves for all 368 documents. **Expert Assist itself was not
run against this folder.** "Consumed by evidence-mining without format errors" is
discharged here as *the format contract holds*, which is what can be checked
from inside this repo; actually running the evidence-mining skill over the
matter is a separate exercise in the Expert Assist repo and it has not been done.

### 9.3 The per-file timeout is reported and NOT fixed

Six documents hit the shipped 3,600 s limit (§3). It would be easy to raise the
default and it is deliberately not raised, for three reasons stated so the
choice can be overturned rather than merely disagreed with:

* **The root cause is unidentified.** The register's Sprint-1 note already says
  so, and that reducing worker counts made throughput *worse*. Moving a timeout
  is a symptom fix for a problem nobody has located.
* **The right number is unknown.** Two documents crossed it on an idle machine
  and six on a contended one. Picking a value from this run would be picking it
  from the contended case.
* **It is a hashed run-identity input** (A-04). Changing the default changes the
  identity projection of every run, which is a coordinator's call, not a
  side effect of an acceptance note.

**Recommendation, not a change:** raise `DOCIQ_FILE_TIMEOUT`'s default only
together with a decision about the extraction-pool behaviour, since the serial
re-read recovered every one of the six — which suggests the pool, not the file,
is what is slow.

### 9.4 Repetition, stated exactly

* **The full-corpus run: ONE run.** Not repeated, and no determinism claim is
  made from it. The byte-identical claim rests on the existing 30-run proof
  (`sprint1_integration_2026-07-31.md`), which is over the fixture corpus, and
  Sprint-1's finding that it is **not** demonstrated on the real corpus is still
  open — §3's unexplained 35-page difference is consistent with that finding
  still being live.
* **A prior attempt at this run was killed externally at ~63 documents** and is
  not reported as a result. The reported run was restarted from scratch.
* **The full suite: 8 consecutive runs**, each a fresh subprocess under a
  different `PYTHONHASHSEED` — see §8.
* **The fail-befores: one mutation each**, applied and reverted; each was
  watched RED against the single test written for it (§3b). One was watched
  GREEN and is reported as such.

### 9.5 Smaller things, recorded rather than left to be found

* The scoped package's scope statement names the matter as
  `dociq_accept_1_8` — the scratch output folder's name. `build_handoff` takes
  the matter name from the output folder, so a real matter folder yields a real
  name. Cosmetic here, and worth knowing it is folder-derived.
* Rebuilding a scoped package **replaces** the run's whole-record
  `upload_package/`, so the matter folder no longer matches the
  `upload_package/*` hashes in its own `output_manifest.json`. Nothing treats
  that as a break (nothing re-verifies a folder against its stored manifest) and
  `verify/manifest.py` now says so — but a reader who assumed otherwise would
  have been wrong.
* The whole-record package is 51.2 MB of text next to a 2.73 GB source. That is
  the reduction the tool actually achieves before any expert lever, and it is
  still ~86× the direct-context reference line.

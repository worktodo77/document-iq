26200, 32 cores, Python 3.14.5, `document-iq\.venv`

Everything below was **run**. Where a claim is an argument rather than a

**A condition on every wall-clock figure in this note.** A second heavy job —

## 0. Headline, stated the way D-25 asked for it

**Criterion 4 is NOT met, and targeted footer re-OCR is not what will close
it.**

The pass does what D-25 ruled: it treats the Bates stamp as its own recognition
problem, and on pages where the whole-page pass returned *nothing*, it returns a
reading. The measurement then runs into a wall that has nothing to do with
resolution:

> **rapidocr reads this production's stamp DIGITS correctly and cannot resolve
> its PREFIX.** On the pages the baseline missed, the band pass returns
> `iCON004926`, `jiCON004926`, `liCON002291`, `TiCON005000` for a stamp that
> reads `iiCON004926`. **The six digits are right nearly every time; the doubled
> lower-case `ii` is wrong nearly every time.**

More resolution makes it *worse* (600 dpi and 800 dpi both score below 400).
Widening the detector's box does not touch it. Binarizing the band helps
slightly and truncates digits elsewhere. This is the recognition model.

It is therefore the first hard, page-level evidence for what D-19 recorded as an
unquantified risk: *"the tool now ships an OCR engine chosen on in-house
familiarity and ONNX bundling convenience, never benchmarked against an
alternative on this corpus."* Per D-25's own terms — *"if it does not [reach
99%], D-19 is back on the table on evidence"* — **this is that evidence**, and
§4.4 sets out the one alternative that would close the criterion without
reopening D-19, and why it is a ruling for Alex rather than a commit.

**The failure direction is preserved: 0 wrong, 0 false positives.** A mangled
prefix does not match the operator-confirmed format, so the page stays a flagged
miss. Nothing in this work can give a page a locator that is not in the
production — §2.2 is the defect that could have, found and fixed before it
shipped.

| | measured |
|---|---|
| criterion-4 baseline, reproduced this session (150 docs / 648 pages, seed 20240529, against the production's own load files) | **593 / 648 = 91.512%** — native **568/568 = 100.000%**, OCR'd **25/80 = 31.250%**, **0 wrong, 0 false positive**, 55 missed |
| what the band pass returns on those 55 missed pages | a stamp-shaped token on nearly all of them, **digits correct**, prefix wrong on ~90% |
| exact-match recovery, best setting (400 dpi) | **1 / 12** and **1 / 10** on two independent page subsets |
| **the full harness re-run** | **did not complete** — see §7.1. This is the gap in the deliverable and it is not dressed up. |

### 1.1 The mechanism

A page qualifies when **both** hold:

1. DocIQ had to OCR it — no usable text layer. A native-text page never pays
   anything, and on the acceptance sample that is **568 of 648 pages**.
2. Its ordinary reading yielded **no stamp-shaped line anywhere in the Bates
   zone** — `bates.zone_has_candidate`, the same grammar detection uses.

For such a page the bottom **1.25 inches** is re-rendered at **400 dpi**, tiled
so no tile is wider than 8:1, and recognized on its own. Only the stamp-shaped
tokens are merged back, appended to the tail of the page text where the zone
sees them. The top band is read too — §4 says "corners/footers" — but only where
the bottom band came back empty.

The trigger is format-agnostic on purpose: extraction is Stage 1 and the format
is not confirmed until Stage 3, so the only answerable question is "did the
ordinary pass produce anything stamp-shaped at all?".

### 1.2 It appends TEXT, never a locator

Nothing in the pass writes `PageRecord.bates`. It contributes candidate text,
which Stage 3 judges with the same grammar and the same operator-confirmed
format as any other text. That is why a misread band cannot become a wrong
locator: `jiCON004926` is not the confirmed format, so it is ignored and the
page stays a miss.

### 1.3 Cost, measured

| | measured on 8 of the baseline's missed pages, same session, same load |
|---|---|
| band pass (bottom, tiled, 400 dpi) | **7.42 s/page, 8.2 Mpx/page** |
| the ordinary whole-page pass on the same pages | **18.80 s/page, 58.5 Mpx/page** |
| ratio | **39%** — and only on the pages that trigger |

On the acceptance sample the trigger reaches at most **80 of 648 pages
(12.3%)**, so the corpus-level cost is bounded by ~12% × 39% ≈ **5% of the
extraction pass**, plus the top band on pages the footer does not resolve.
Two further bounds keep that true on shapes this sample does not contain — a
per-page pixel ceiling (§2.3) and a per-document calibration (§2.5).

## 2. Defects found and fixed

Five, all fixed here. Three of them were found by *measuring*, not by reading.

### 2.1 The appended block could evict the page's own reading

Appending to the tail is what makes a recovered stamp reachable, and it is also
what pushes the existing tail out of the zone — turning pages `apply_bates`
currently gets right, via the confirmed-token search, into misses.

Fixed by construction: `BatesZone.tail_lines` is
`_TAIL_LINES_BASE + FOOTER_BLOCK_MAX_LINES` (4 + 4 = 8), and a test asserts the
relation so raising one without the other fails. A parametrized test walks
**every** combination of original-tail length × appended-block length up to both
bounds.

**Fail-before, watched:** with the margin removed, **10 of 16** parametrized
cases go red.

### 2.2 An anchored line outranked a folded one — RIGHT could have become WRONG

The serious one. It did not exist until D-25 created it.

`apply_bates` ran the whole-line anchored match first and fell back to the
confirmed-token search only for pages with no anchored line. The band pass
appends a recovered token **as its own line**, which is anchored. A band pass
that misread one digit would therefore produce an anchored `iiCON003945` that
beat the folded, correct `iiCON003944` already in the zone — turning a right
answer into a **wrong** one, the outcome §4 rates worse than a miss.

There is one rule now (`_zone_stamp`): every confirmed-format match anywhere in
the zone is collected, and two different ones are a **refusal**, wherever they
came from. The anchored case is a special case of it, not a privileged path.

**Fail-before, watched:** restoring anchored-first turns the disagreement test
red, and it fails by producing `iiCON003945` — the wrong locator, exactly.

### 2.3 The band was a fraction of page height, which is wrong twice over

Found by measuring. The acceptance corpus contains pages whose box is
**2700 × 3681 points** — photographs 37 by 51 inches — and 3600 × 2761
landscape ones.

* **Cost.** 14% of a 51-inch page is a seven-inch strip: 15000 × 2863 px at 400
  dpi, **43 Mpx per band**. Mean band over the 55 missed pages was 35 Mpx at 400
  dpi and 79 Mpx at 600. A sweep **did not finish in 90 minutes** and was
  killed.
* **Correctness.** At 3600pt wide the strip is **13:1**, past rapidocr's
  `width_height_ratio` of 8. The engine then **skips text detection entirely**
  and recognizes the whole strip as one line. Measured directly: the bottom
  strip of `iiCON004938.pdf` p1 and `iiCON006088.pdf` p1 returned **nothing
  readable at all** — on precisely the pages the pass exists for.

A Bates stamp is burned in at a physical size a physical distance from the
physical edge. Measured on this corpus it sits within **~26–40 points of the
bottom edge** whether the page is letter-size or four feet tall. So the band is
**1.25 inches, always**, and it is **tiled** at the engine's own aspect limit
with a fifth of a tile of overlap so a stamp cannot be cut in half.

A tile is at most `band × 8·band` — **~1.7 Mpx at 400 dpi whatever the page
is** — and the tile *count* grows with page width alone. The 43 Mpx band became
5 tiles totalling ~10 Mpx, against the 77 Mpx the ordinary pass already
rasterizes for the same page. **Thirteen page shapes are asserted**, including
the three real ones from the corpus, a page smaller than the band is deep, and
four degenerate ones (a 612 × 0.1pt page would otherwise have been nearly a
thousand recognitions; the tile count is capped at 12 and the cap is stated).

### 2.4 Each tile re-decoded the page image

`get_pixmap(clip=...)` per tile decodes the page's embedded image every time. On
this corpus a page is a 230 MB photograph, so five tiles top and bottom meant
**ten full decodes of it**. The acceptance re-run passed 90 minutes at 0.5 cores
and 13 GB resident and had to be killed. The band is now rendered **once** and
sliced with numpy views. The 39% figure in §1.3 is after this fix.

### 2.5 "Only where it can help" is a per-PAGE test, and that is not enough

The one that cost the most machine time. On an image-only document **every page
qualifies**, so two bands × five tiles × 300 pages is three thousand
recognitions for one document. That is not hypothetical: the criterion-4 re-run
was doing it, passed **nine hours**, and was killed.

Where a production burns its stamp is a property of the **production**, not of
the page. The pass now **calibrates**: the first four qualifying pages are
probed on both bands; after that only the band(s) that actually read something
are used; if neither read anything, the pass stops for that document and the
notes report how many pages it declined to re-read. An unreadable scan costs
**eight** recognitions instead of three thousand; a stamped production resolves
on its first probed page and keeps everything it was going to get.

**Fail-before, watched:** with the probe unbounded, the unreadable-scan test
goes red at 120 band reads instead of 8, and the header-stamped test goes red
because every page keeps paying for a footer band that never works.

### 2.6 A latent hazard, recorded rather than triggered

`RapidOCR.__call__` mutates the **shared** detector's `box_thresh` and
`unclip_ratio` when passed per-call keyword arguments, and does **not** restore
them. One call with tuning parameters would silently re-tune every later call in
the process, making a run depend on document order. DocIQ never passes them —
this was found while testing whether detector tuning fixed the prefix (§4.3) —
so it is a hazard, not a live defect. It is recorded because the fix is "never
pass them", which is invisible in the code.

## 4. What the band pass cannot fix, with the evidence

All three probes below run DocIQ's shipped `_band_tiles` / `ocr_lines` /
`stamp_tokens` over pages drawn from the baseline's own miss list — not a
re-implementation.

### 4.1 Resolution and band height (12 pages, tiled 1.25in band)

| setting | exact | what it returned otherwise |
|---|---|---|
| 300 dpi | 1 / 12 | `iCON…`, `jiCON…` |
| **400 dpi** | **1 / 12** | `iCON…`, `jiCON…` |
| 600 dpi | 0 / 12 | `jiCON…`, one truncation `CON005` |
| 400 dpi, 2in band | 0 / 12 | `iCON…`, `jiCON…` |

The digits are correct in **every** one of those readings. Only the prefix is
wrong, and always the same way: `ii` resolves to one glyph, or to `j`, `l`, `T`.

### 4.2 Preprocessing is not the variable (10 pages)

| variant | exact | note |
|---|---|---|
| 400 dpi raw | 1 / 10 | |
| 400 dpi + Otsu binarization | 3 / 10 | but truncated digits on one page (`jiCON005`) |
| 400 dpi grayscale | 1 / 10 | |
| 250 dpi raw | 0 / 10 | |
| 250 dpi + Otsu | 1 / 10 | |
| 800 dpi raw | 0 / 10 | five pages returned nothing at all |

Otsu binarization is **measured and not adopted**: better on the prefix on ten
pages, and it shortened a digit run on another. Adopting an image transform that
can shorten a digit run, on that evidence, would be tuning towards a number
rather than towards a correct locator. It is recorded here so the next person
does not have to rediscover it.

### 4.3 Detector tuning is not the variable either (10 pages)

The obvious hypothesis was that the detection box starts a glyph too far right
and clips the first `i`. Tested by passing the engine `unclip_ratio` and
`box_thresh` directly:

| variant | exact |
|---|---|
| default (1.6 / 0.5) | 1 / 10 |
| unclip 2.2 | 0 / 10 |
| unclip 3.0 | 0 / 10 |
| unclip 2.2, box_thresh 0.3 | 0 / 10 |

Widening the box does not recover the glyph. It is not a cropping problem.

### 4.4 What WOULD close it — a ruling, not a commit

The prefix carries **no per-page information**: every page of a confirmed
production has the same one. Normalizing a near-miss prefix to the confirmed one
— with digits, digit width, separator and suffix all matching exactly — would
convert most of this residue into correct locators, and could not point at a
*different page*.

It is **not** done here, and the reason is not timidity:

* §4 requires misses to be **flagged, not silently corrected**. Writing
  `iiCON004926` where the page reads `jiCON004926` is a silent correction.
* `bates.py` states as a deliberate rule that `iiCON` and `IICON` are two
  formats and neither is applied to the other's pages, *"because a locator
  pointing at a record that does not exist is worse than no locator."* Prefix
  normalization softens that rule for OCR'd pages.
* On a corpus holding both an `iiCON` and a real `iCON` production it would
  misattribute — narrow, but real.

**This is a decision for Alex with numbers attached**, and it is the trade D-25
reserved. The alternative on the table is D-19.

## 5. Determinism (criterion 7)

Determinism is asserted where the pass can break it, and the counts are the long
ones the standing rule requires for anything OCR- or ordering-sensitive:

| probe | result |
|---|---|
| `_extract_pdf` over a scanned fixture, band pass live, **×30 runs** | byte-identical text, notes and per-page `ocr_conf` every run |
| the per-document **calibration**, ×30 runs on a 15-page scan whose bands resolve unevenly | identical text and notes every run |
| `stamp_tokens` over a mixed line, ×30 | one distinct result |
| nothing about the attempt reaches the page | asserted: no dpi, band, retry count, marker or timing appears in any page's text |
| tiles assembled in **submission** order, never completion order | the rule `_ocr_pdf_pages` already followed, applied to a pass that fans out per tile |
| full suite, **1,016 tests** | green, run repeatedly through the session |

The trigger, the calibration and the token reduction are all pure functions of
page bytes in page order. No wall-clock value, retry count or resolution enters
hashed content.

**Not re-proven here:** the end-to-end `dociq.selftest --runs N` byte-identical
corpus proof. Track F could not complete it on the source tree either (its run
was killed under load and the note says so). It is §7.3.

## 7. What is NOT proven

Stated plainly, because a dressed-up shortfall is worthless.

### 7.1 The full harness re-measurement did not complete

The after-number for criterion 4 is **not** measured by the harness. Three
attempts were made and each was killed:

1. the first exposed the per-tile re-decode (§2.4) — 90 min, killed;
2. the second exposed the per-page cost on image-only documents (§2.5) — 9
   hours, killed;
3. the third, with both fixed and restricted to documents the pass can reach,
   was still running at ~7,100 s of CPU when the session ended.

What the box was doing throughout is in the preamble. What §4 measures directly
— that the band pass recovers the digits and not the prefix — is the reason the
after-number is expected to move by a few pages rather than to 99%, but **that
is an inference from the page-level probes, not the harness figure**, and it is
labelled as one.

To finish it, from `C:\Users\Alex\document-iq-wt\bates` on an unloaded box:

```
PYTHONPATH=src python tools/bates_acceptance.py \
  --corpus "C:\Users\Alex\Desktop\Files for Claude\20240529" \
  --sample-docs 150 --max-mb 15 --seed 20240529 --out after.json
PYTHONPATH=src python tools/bates_acceptance.py \
  --corpus "C:\Users\Alex\Desktop\Files for Claude\20240529" \
  --sample-docs 150 --max-mb 15 --seed 20240529 --no-footer-reocr --out before.json
```

The second command produces the before-number **with the after-code**, which is
the only honest way to attribute the delta. `--only-ocr-docs` on both makes it
cheaper and is sound: the band pass is reached only when the OCR map is
non-empty, and a test asserts that a document with no OCR'd page comes out
byte-identical either way.

### 7.2 The negative control was NOT re-run

**This is the most important gap.** The 298-PDF / 17,732-page Petrobras corpus
is D-13's designated negative case, and higher-resolution footer OCR on unstamped
material is exactly the change that could start proposing a format where none
exists. It was not run, for the same machine reason.

Three things bear on the risk, and none of them is the measurement:

* the pass fires only on pages DocIQ had to OCR **and** whose zone already holds
  no stamp-shaped line — and Petrobras is overwhelmingly native text;
* what it appends is bounded to four short tokens accepted by the **same**
  grammar detection already applies, so it introduces no shape the detector did
  not already admit;
* `propose_format`'s 50%-per-document coverage bar, the fix that made the
  previous negative-control run come back clean, is untouched.

That is an argument. **Run the measurement before this branch merges:**

```
PYTHONPATH=src python tools/bates_acceptance.py \
  --negative-control "C:\Users\Alex\Desktop\Petrobras\Petrobras\Project FIles" \
  --negative-limit 400 --out negative.json
```

It must report **no format proposed** and **0 false positives**.

### 7.3 The source-tree end-to-end determinism proof

`python -m dociq.selftest --runs 8` was not run to completion in this session.
The unit-level determinism evidence in §5 is real and is at the ×30 count, but it
is not the same claim as the whole pipeline emitting byte-identical output.

### 7.4 The band pass has never been measured on a header-stamped production

The top band is implemented, tested and calibrated against, but no corpus
available here stamps its header. That path is exercised by unit tests only.

## 8. Stop-the-line

Nothing in this work touched `src/dociq/contracts.py`, `src/dociq/gui/*`,
`src/dociq/adapter.py` or `packaging/`, and no shape change to any of them is
needed: everything D-25 required fits inside the extractor and Stage 3.

**One decision is owed (§4.4):** whether a recovered stamp whose digits match the
confirmed format exactly, but whose prefix is a near-miss, may be normalized to
the confirmed prefix. It is the only change identified that would move criterion
4 materially without reopening D-19, and it trades against §4's "flagged, not
silently corrected".
